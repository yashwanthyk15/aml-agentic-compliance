# AML Agentic Compliance System

A local-first, multi-agent AML investigation and regulatory compliance system for a bank's compliance desk. The system ingests public regulatory PDFs, synthetic transaction data, and OFAC sanctions lists, then routes natural-language queries through three cooperating agents with data-layer RBAC, PII masking, and a feedback-driven ranking loop.

## Architecture

```
USER
  ↓
AUTHORIZATION + RBAC + PII MASKING
  ↓
QUERY ROUTER (deterministic)
  ↓
AGENT 1: COMPLIANCE SCREENER (LLM)
  ↓ ScreeningAlert
AGENT 2: INVESTIGATOR (LLM)
  ↓ InvestigationResult
AGENT 3: RECOMMENDER (LLM)
  ↓ Recommendation
POLICY VALIDATOR (deterministic, no LLM)
  ↓
EXPLAINABLE RESULT + AUDIT TRAIL
  ↓
ANALYST FEEDBACK → FUTURE RANKING
```

### Why Three Agents?

Each agent has a distinct, non-overlapping responsibility:

| Agent | LLM? | Job |
|-------|------|-----|
| Compliance Screener | Yes | Detect signals, retrieve evidence, create alert |
| Investigation Agent | Yes | Evaluate supporting/contradictory/missing evidence |
| Recommendation Engine | Yes | Produce constrained decision-support recommendation |
| Policy Validator | **No** | Deterministic safety/policy validation |

The Recommender consumes the typed `ScreeningAlert` and `InvestigationResult` — a genuine handoff with schema validation, not a text blob.

## Data Sources

| Source | Type | Description |
|--------|------|-------------|
| FATF Recommendations (Feb 2025) | Regulatory PDF | International AML/CFT standards |
| FATF Risk-Based Approach | Regulatory PDF | Supervision and enforcement guidance |
| RBI KYC/AML Master Direction | Regulatory PDF | India-specific KYC/AML obligations |
| OFAC SDN Enhanced XML | Sanctions XML | US sanctions/watchlist data |
| Synthetic dataset | Generated CSV | ~2000 transactions, ~300 customers, ~500 accounts |

**No real customer data or PII is used.** All customer data is synthetic, generated by `scripts/seed_data.py`.

## Quick Start

### Prerequisites

- Python 3.12+
- Docker Desktop (for PostgreSQL + Qdrant)
- A Google Gemini API key

### Setup

```bash
# 1. Clone the repository
git clone https://github.com/yashwanthyk15/aml-agentic-compliance.git
cd aml-agentic-compliance

# 2. Create virtual environment
python -m venv .venv
.venv\Scripts\activate      # Windows
# source .venv/bin/activate  # macOS/Linux

# 3. Install dependencies
pip install -r requirements.txt

# 4. Configure environment
copy .env.example .env
# Edit .env and add your GEMINI_API_KEY

# 5. Start infrastructure
docker compose up -d

# 6. Generate synthetic data
python scripts/seed_data.py

# 7. Run ingestion pipeline
python scripts/ingest.py

# 8. Generate understanding files
python scripts/generate_understanding.py

# 9. Seed user profiles
python scripts/seed_users.py
```

### Usage

```bash
# CLI query
python query.py --role AML_ANALYST "Which transactions triggered the structuring rule?"
python query.py --role CCO "What does the RBI guidance say about customer due diligence?"
python query.py --role EXTERNAL_AUDITOR "Show the audit trail"

# Run evaluations
python evals/run_evals.py

# Feedback demo (before/after ranking)
python scripts/demo_feedback.py

# Streamlit UI
streamlit run app/ui/streamlit_app.py
```

## RBAC & Security

RBAC is enforced **at the data layer**, not in the UI or in prompts. The model never sees data the user isn't authorized to access.

| Role | Transactions | Customer PII | Alerts | Audit | Identity Docs |
|------|-------------|-------------|--------|-------|--------------|
| CCO | Full | Full | Full | Full | Full |
| AML Analyst | Flagged only | Masked | Full | Scoped | Denied |
| External Auditor | Denied | Denied | Audit view | Full | Denied |
| Relationship Manager | Own portfolio | Masked | Own portfolio | Denied | Denied |

**PII masking examples:**

```
CCO sees:         Rahul Kumar     | 472900183728     | rahul@example.com
AML Analyst sees: R**** K****     | ********3728     | r***@example.com
Auditor sees:     CUSTOMER_REDACTED | ACCOUNT_REDACTED | [DENIED]
```

The authorization flow:
```
authorization → filtered query → masked data → LLM
```
NOT:
```
retrieve secret → send to LLM → tell LLM not to reveal it
```

## Feedback Loop

Analyst dispositions feed back into alert ranking:

```
TRUE_HIT     → 1.50× multiplier (promote similar patterns)
FALSE_POSITIVE → 0.70× multiplier (demote similar patterns)
ESCALATED    → 1.20× multiplier (increase attention, not confirm)
```

Feedback modifies **prioritization only**. It cannot modify regulatory truth, sanctions data, or authorization rules.

Run `python scripts/demo_feedback.py` to see a concrete before/after ranking demonstration.

## Prompt Injection Defense

Transaction narratives, counterparty names, and remittance text are **attacker-controlled** fields. The system:

1. Scans for known injection patterns (deterministic regex)
2. Labels all external text with trust levels (ATTACKER_CONTROLLED_DATA)
3. Builds agent context with trust boundary markers
4. Logs injection events in the audit trail
5. Never executes instructions embedded in data fields

The actual security boundary is `authorization + data filtering + trust labeling`, not a prompt instruction.

## What Breaks at 100×

### 1. Transaction Database — PostgreSQL Under Pressure

**Current:** ~2,000 synthetic transactions in CSV, loaded into memory.

**At 100×:** Millions of transactions per day. The current approach of loading full CSV into pandas breaks immediately — memory exhaustion, no indexing, no partitioning.

**Failure modes:**
- Full-table scans on unpartitioned data → query latency spikes from ms to minutes
- Write contention on the alerts/feedback tables during peak processing
- The deterministic screening rules currently iterate all transactions in-memory — at 100× this becomes a batch job, not a real-time operation

**What changes:**
- PostgreSQL with time-based partitioning on the transactions table
- Streaming ingestion (Kafka/Debezium) replacing batch CSV loads
- Materialized views for precomputed aggregates (daily velocity, rolling amounts)
- Read replicas to isolate analytical queries from operational writes
- The screening rules move to SQL window functions or a dedicated stream processor

### 2. Regulatory Retrieval — Vector Search Quality Degrades

**Current:** ~500 regulatory chunks from 3 PDFs in local Qdrant.

**At 100×:** Thousands of pages across dozens of jurisdictions, multiple versions per regulation, overlapping obligations.

**Failure modes:**
- Retrieval precision drops as the corpus grows — more irrelevant chunks compete for top-k slots
- Version confusion: the system might cite a superseded regulation without detecting the version conflict
- Cross-jurisdiction queries retrieve evidence from the wrong jurisdiction's rules

**What changes:**
- Mandatory metadata filtering (jurisdiction + version) before vector search
- Two-stage retrieval: coarse metadata filter → fine semantic search → reranker
- Explicit version graphs so the system knows which regulation supersedes which
- Separate collections per jurisdiction to reduce cross-contamination

### 3. LLM API — Rate Limits and Latency

**Current:** Sequential single-user calls to Gemini Flash.

**At 100×:** Hundreds of concurrent compliance analysts generating 3 LLM calls per query (screener + investigator + recommender).

**Failure modes:**
- Gemini API rate limits (RPM/TPM) hit within minutes under concurrent load
- P99 latency goes from ~2s to 30s+ as the queue backs up
- Cost scales linearly with users — no caching means identical regulatory questions regenerate answers

**What changes:**
- Async worker pool with priority queuing (urgent alerts skip the queue)
- Response caching for identical regulatory questions (same query + same evidence → cached answer)
- Model routing: simple queries go to a faster/cheaper model, complex investigations go to the full model
- Circuit breaker pattern: if the LLM is down, degrade to deterministic screening + manual review

## Technology Stack

| Component | Technology | Why |
|-----------|-----------|-----|
| Language | Python 3.12 | Data tooling, Pydantic, LLM SDKs |
| LLM | Google Gemini 2.0 Flash | Fast, structured output, free tier |
| Embeddings | all-MiniLM-L6-v2 (local) | No API cost, deterministic |
| Vector DB | Qdrant (Docker) | Semantic search with metadata filtering |
| Relational DB | PostgreSQL 16 (Docker) | Transactions, alerts, audit trail |
| PDF | PyMuPDF | Page-level extraction with metadata |
| XML | lxml | OFAC SDN structured parsing |
| Fuzzy matching | rapidfuzz | Sanctions candidate generation |
| Data contracts | Pydantic v2 | Typed agent handoffs |
| Testing | pytest | Unit and integration tests |
| UI | Streamlit | Minimal walkthrough demo |
